# Platform assistant and sandbox sessions

The Console's assistant is a second author beside a customer's coding agent. MCP stays the primary surface; both reach the same domain services.

## Loop

- A thread is `AssistantThread` plus an append-only `AssistantEvent` log (`user`, `assistant`, `tool_result`, `status`, `summary`). The log is the model context, the transcript and the stream cursor. No process holds state between steps. A thread belongs to the project and may name the record it was opened on (`subject_kind`, `subject_id`; `threads.SUBJECTS` maps a kind to its model, today only `dataset`). A record has at most one thread.
- `services/assistant/loop.py:advance` runs one step: end a wait, deliver a queued `AssistantInput`, run one pending tool call, or stream one model reply. `tasks/assistant.advance` (queue `assistant`) re-enqueues itself while a step is due.
- A step holds a claim (`AssistantThread.claim`) and writes only through it: `log.append(..., claim=)` and `_held(thread)`. A step that outlives `LEASE` loses the claim to the next one, which marks the run `interrupted`; the old step can then write nothing. An interrupted run is never resent to the model: the user continues it.
- States: `idle` (only a queued message starts it), `ready` (a step is due), `running`, `waiting` (holds for jobs). `tasks/assistant.reconcile` (beat, 5 s, queue `control` so that long model replies cannot starve it) only reads `loop.due()` and enqueues `advance`; every decision is made in `advance` under the thread's row lock.
- A tool that starts jobs puts the thread in `waiting` on all of them. `assistant/jobs.py:KINDS` names each job kind's model, state field and resting states: a job rests when the platform will not move it again by itself. The reconciler asks one query per job kind, however many threads wait. A new job kind a tool can start needs an entry there, or the thread does not wait for it. An urgent ("send now") message ends a wait while the jobs still move; `get_job` on a moving job waits for it again.
- A message for a dataset whose source still lands waits in the queue: the landing composer sends at once and the first step runs when the source has landed.
- When a reply's prompt passes `ASSISTANT_COMPACT_TOKENS`, the next step appends a `summary` event. A step reads only the newest summary and the events after its `through`; the log and the transcript keep everything. The cut never separates a tool call from its result.
- Stop takes effect at the next step boundary and removes queued messages. A wait ends at once: its call is answered with what the jobs are now, a pipeline run or a handoff is cancelled, and other started jobs continue (the status says how many).
- The sender of the newest message pays for the model calls (`BillingService.DATA_WORKSHOP`) and tools run with that sender's project access, checked on every step and call. A reply and its charge are saved in one transaction. A reply the user stops in the middle is not charged: the provider reports no usage for it.

## Tools

- `services/assistant/tools.py`: a thread offers `BASE_TOOLS` plus the `TOOLSETS` it opened (`data` by default; `open_toolset` adds `training`, `evaluation`, `inference`, `observability`), because every schema costs tokens on every reply. They are MCP catalog tools called in process through `CATALOG.invoke` with a `PlatformCredential`; validation and receipts are the catalog's own. The loop supplies `project_id`, and `request_key` on mutating tools.
- A mutating catalog tool with cost class `llm` or `gpu` is paid work. The call is refused and the refusal shows the user a Choices; the approval is the user's answer to that refused call. One approval starts one call: its request key is derived from the approved refusal, so a repeat before the result is recorded returns the first receipt, and the result marks the approval used. The approver pays. A thread with no approving user never starts paid work.
- Own tools need the kernel, the result panel or the thread: `stage_dataset`, `run_python`, `write_pipeline_package`, `present`, `open_toolset`, `hand_off`.
- `hand_off` gives work that needs the customer's repository to their coding agent: an `AssistantHandoff` the agent reads with the MCP tool `list_assistant_handoffs` and answers with `complete_assistant_handoff`. The thread waits for it like a job.
- Publication has one path: a retained pipeline package run by the pipeline runner. The kernel is for exploration only.
- `present` documents are validated by `services/assistant/presentation.py` and stored in `AssistantEvent.presentation`, apart from the payload the loop reads. Charts, tables and metrics read tables the kernel wrote, and an Image is a PNG, JPEG or WebP file it wrote, retained under `MEDIA_ROOT/assistant/<thread>/` by content name; the Console renders the fixed component set in `frontend/src/components/assistant/`.
- A Question or Choices answer is `{"call", "id", "values"}`: the tool call that showed it and the component's id there. The model may reuse an id; the call makes it unique.

## Sandbox sessions

- `services/sandbox_sessions/` is one contract: `start`, `execute`, `put_file`, `get_file`, `stop`. A provider is one module and one entry in `PROVIDERS`; `SANDBOX_SESSION_PROVIDER` selects it.
- Every provider runs `sandbox/kernel.py` (standard library only) and gives the same layout: a writable working directory, inputs read-only at `../inputs/`.
- A session is a cache (`services/assistant/sessions.py`). The platform starts one on a thread's first cell and admits it within `ASSISTANT_PROJECT_SESSIONS`: at the limit the conversation idle longest gives way. Providers close an idle session after `sandbox.sessions.IDLE_SECONDS`. Whenever a thread's session is gone, `kernel_lost` holds the reason; the next `run_python` starts a session with the staged datasets back, does not run its code and tells the model why the kernel is new. Staged datasets are limited to `STAGED_BYTES`.
- `native` runs sessions in the `sandbox` service (`sandbox/sessions.py`) under the uid and memory admission of a pipeline run, from the same memory budget. Sessions live in one server's memory, so a native session ID is its URL on that server: with several servers behind `SANDBOX_URL`, each sets `SANDBOX_ADVERTISE_URL` to an address the workers reach, or sessions are lost at once. A server that is gone while the service answers took its sessions along (`SessionGoneError`); a service that does not answer may come back with them (`SessionUnavailableError`). The server holds a kernel's reply to one size and one deadline, because the kernel runs the tenant's code.
- Native sessions, pipeline package runs and document extraction share one container and one Linux kernel. A uid keeps a run out of another's files, and `kernel.py:confine` closes the rest without any privilege (the container cannot hold `CAP_SYS_ADMIN` on Fargate, so there are no per-run namespaces): Landlock limits the process and its children to the run's own folders, the libraries and its own `/proc` entry, denies TCP and scopes signals and abstract sockets; a seccomp filter refuses every socket family but `AF_UNIX`. Landlock applies as far as the host's Linux supports it (files 5.13, TCP 6.7, scoping 6.12); `/health` reports its version as `landlock`, and 0 means runs are apart by uid alone. A library that cannot reach a file it needs may abort the process instead of raising, so `conformance.LIBRARY_USE` uses every pinned library; a new library or a new allowed path is checked there. The shared kernel remains: where customers who do not trust each other share hardware, use a provider that gives each session its own sandbox.
- `daytona` creates one network-blocked sandbox per session from the snapshot `manage.py build_session_snapshot` builds; the snapshot name hashes the kernel and the whole image recipe, so a release that changes either needs a build before sessions start.
- `conformance.py` holds the contract checks. The test suite runs them on `native`; `manage.py check_sandbox_sessions` runs them on the configured provider, which is the only way to check a hosted one (tests cannot reach the network). `.github/workflows/sandbox-sessions.yml` runs it on Daytona each day and on a change to the adapter, the kernel or `uv.lock`; it needs the repository secret `DAYTONA_API_KEY`.
- Persistence belongs to the platform. A provider's workspace persistence, snapshots of user state and stop-resume are not used.

## Stream

`GET /api/assistant-threads/{id}/events/?after=N` sends every event after the cursor, then the thread with its queue, then live changes. Postgres is the record; Redis only signals `changed` and carries the reply being written: the draft key holds its text so far for a stream that opens in the middle, and the channel carries what it gains.
