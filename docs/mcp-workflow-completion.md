# MCP workflow completion

Implement the mechanics review using shared domain services. Preserve existing data and completed runs. No real provider submissions are part of implementation validation.

Failure cases to verify before implementing the affected behavior:

- A selected frozen parent is replaced by the active cell; derivation changes the old chain or loses lineage.
- Sampling silently changes supervision, rejects valid mean-only targets, or attempts an impossible coverage budget.
- An unknown Workshop selector is ignored and reads a different version.
- Drafting a comparison submits paid work; repeating launch duplicates it; a draft starts through reconciliation.
- A client reconnect cannot discover the objective, inputs, unresolved decisions and next supported operation.
- A worker crash loses progress or repeats an acknowledged provider request; one failed arm prevents independent work.
- External chunks repeatedly hash complete suites, scan earlier input, or issue one query per result during export.
- Cached predictions are reused for different inputs, identities, inference conditions or tenants.
- An unfamiliar recipe has no bounded measurement path; authorization does not match the forecast and launch configuration.
- Stopping observation is confused with stopping execution; paused work is advanced by reconciliation.
- Successful child runs leave an experiment permanently launched, or failed/missing outputs are reported complete.
- Typed contracts, REST, MCP, generated clients, installed skills and deployed-runtime guidance disagree.

Validation uses public MCP transport journeys, real database/file artifacts and mocked provider boundaries, supplemented by targeted recovery and tensor checks. Record command, fixtures, environment and observed results. Live hardware qualification remains a separate authorized operation.
