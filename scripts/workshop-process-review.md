# Coding-agent data preparation review

Reviewed 6 November 2026. This is a process review, not a new certification of the historical datasets or models.

## Coverage and evidence

The local Codex catalogue exposed 236 chats (220 unarchived, 16 archived). Title screening selected 55 preparation/training chats. At least one history page was retrieved for 54: 40 complete histories and 14 partial histories. One selected history exceeded the reader's size limit even with a reduced page. Unrelated chats were catalogued, not read in full. This is not a claim to have read every turn in all 236 chats.

The review used user requests, assistant reports, command/tool records and retained results. A proposed plan, a prompt drafted for another agent, a blocked run and a completed transformation are different kinds of evidence. Historical assistant statements are reported observations unless corroborated by commands/results. No historical requests authorise new platform operations. No chat transcript, benchmark answer or credential is loaded into the native agent.

## The operating method

1. **Define the gap.** Infer the example unit, prediction/use setting, consumer and candidate supervision from source and platform context. Preserve ambiguity. A capability name is not a label definition.
1. **Inspect before committing.** Pin original bytes/cells; compare landed and original types; sample ordinary and exceptional records; measure full-population invariants where possible. Ask a concrete question of each experiment.
1. **Plan around checks.** Keep a short evolving sequence of goals, explicit checks and one active step. Decide how to detect a wrong result before scaling the transformation. The plan is agent-authored; minimal user intent remains sufficient to begin investigation.
1. **Test independently.** Verify actual values against independently expressed source rules. Exercise false-like strings, missingness, rare classes, boundaries and nested data as applicable. Equal row counts, valid JSON and a zero exit code do not establish preservation. Expansion and aggregation need their own cardinality and lineage checks.
1. **Revise from evidence.** Record the observed failure separately from a suspected cause; run a test that distinguishes explanations. Recheck the failed condition and affected downstream checks. Preserve pending/unknown provider outcomes and reconcile them without resubmission.
1. **Verify the handoff.** Retain code and pinned inputs, preview, publish and inspect the exact output. Recheck values, lineage, consumer compatibility, split relationships and coverage. Keep technical validity, semantic evidence and model performance separate.

## Implementation

`record_workshop_plan` stores the intended outcome, consumer, ordered steps and their checks, uncertainty, next action and failure investigations. This complements the training assessment: the assessment captures target/supervision interpretation; the work plan controls execution and verification for any objective.

The plan explicitly sequences **orientation → transformation → verification**. Orientation records pinned source identity, actual data-observation receipts, example unit and structure, intended use, field/family meanings and roles, availability at use, risk-specific checks and the required changes. Format documentation, an export receipt or a proposed plan alone cannot establish orientation. A field declared available only after the outcome cannot simultaneously be an inference input. The agent can return to orientation when contradictory evidence changes its interpretation. Unknown and inferred meanings remain distinct from observations; no universal target or dataset taxonomy is imposed.

Tool availability reflects this sequence. Before a plan, read-only investigation remains available. With an orientation plan, workspace experiments and source operations are available, while retained transformations, derivations, publication, bindings and partitions remain unavailable. Recording source-backed orientation and moving to transformation opens those tools. After an undiagnosed failure, mutation tools are withheld until the plan records a hypothesis and next test; invocation checks enforce the same rule. Arbitrary workspace Python is still needed for exploration and can write files: phase controls govern the platform handoff, not a claim to recognise the semantic purpose of arbitrary code.

Before workspace writes/commands/package retention or mutating platform tools, the runtime requires a recorded plan with an active step. Read-only investigation and environment preparation remain available. After a failed action, the latest failure must have a hypothesis and next test recorded before another mutation. A verified step must cite a prior successful execution/data observation; notes, file writes, other plans, unknown receipts and failed commands cannot serve as evidence. Resolved failures need later successful observations. The latest plan and observed unresolved failures survive context trimming; dropping a diagnosis from a later plan does not erase its history.

Completion proposals return corrective feedback if steps remain unverified or the final check predates subsequent workspace execution or publication. Because arbitrary shell commands can mutate files, the final-check freshness rule is conservative. The workflow guide teaches source/output comparisons, independent checks, unsupported-consumer handling and hypothesis-driven recovery without embedding dataset targets or recipes.

MCP impact: the native internal tool is available through the existing reasoning harness; its plan and failures are ordinary retained action receipts inspected through the existing project-scoped Workshop task surface. No new public endpoint, model, migration or generated client is required. The runtime image/dependencies, training and inference providers are unchanged.

## Limits and qualification

Receipt attribution and ordering cannot prove that an agent-written test is meaningful, that its hypothesis is correct, or that it selected the right intent. An agent can still write a vacuous assertion; this implementation does not label it independent semantic certification. No universal checklist covers every modality. Unsupported requests and unresolved semantics remain explicit outcomes. There is no task token budget or new action-count cap.

The ongoing Titanic trial was paused at step 353 before this update. Its latest proposed check searched code for field names, which cannot detect the previously observed false-like string coercion error. Historical successes do not qualify the new harness; current tests and a live continuation must be reported separately.

Validation: 40 focused runtime/agent cases passed across the suite and targeted correction runs; the Data Workshop journey passed in 62.43 seconds. Hooks and whitespace checks passed. Tests exercise rejected evidence references, failure retention, stale final checks, state-dependent tool availability, actual-data requirements for orientation, declared post-outcome input rejection and returning to orientation. They do not establish model quality or prove that all meaningful risks were discovered.
